If `tool_use_id` is missing from the payload the command is left unwrapped rather than leaking an orphan file. `on_post_tool_use` looks up `payload["tool_use_id"]` in the pending map, calls `parsers.read_rc_file(rc_path)`, sets `exit_code`/`input.resolved_bin` on the ledger events, then unlinks both the rc file and the map entry. Real Bash tool output is stored untouched -- there is nothing in stdout for a later turn to have seen and imitate. Stale pending entries from a call whose `PostToolUse` never fires (interrupted mid-run) are a minor cleanup gap, not a correctness one. |
| E9 | Claude Code stores no exit code for Bash. Summary parsing vs PreToolUse wrapping vs Tier 3 re-run? | Oliver | decided | All three, in that order. **VERIFY resolved by experiment (2026-09-19): the wrapped command's trailer IS visible to the model** — a live `pytest --version` under the hook returned `__RECEIPTS_BIN=…` and `__RECEIPTS_RC=0` in the agent's own tool output. So the stdout trailer must go: write it to a per-call file instead (issue #22). MECHANICS §2. |
| E10 | Subagent laundering: may a parent's claim be confirmed by a *subagent's* tool call? | Oliver | decided | **No -- evidence for a parent's claim about its own work is main-chain only, never, full stop.** `rules._visible` and `review.annotate` independently drop every `sidechain` event; that agreement is now the intended rule rather than a coincidence, pinned by Anush's `tests/unit/test_sidechain_laundering.py`. Rationale in docs/MECHANICS.md §1: (a) the lenient rule reintroduces multi-agent laundering, where a critic subagent approves a false narrative and the parent inherits it; (b) a parent that delegated did not witness the run, so the honest claim is about delegation, a different sentence with a different truth condition; (c) nothing goes unverified, because `SubagentStop` gives the subagent its own receipt against its own main-chain ledger; (d) the costs are asymmetric -- strict fails to an `unwitnessed` mark on honest work, which is never an accusation and which the agent clears by re-running the check itself, while lenient fails to a `confirmed` on a laundered claim, the one outcome this project must not produce. |
| E6 | Claim extraction: LLM vs regex? | Oliver | decided (provisional) | **Per-sentence classification leads; regex is the no-key fallback.** Measured on 204 gold sentences (eval/results/2026-09-19-extraction.md): regex R=0.14/P=0.60, whole-report LLM R=0.32/P=0.87, per-sentence gpt-5-mini R=0.95/P=0.57, per-sentence gpt-5.2 R=0.68/P=0.83. Labels are machine-made and unstable run to run, so this orders the options rather than measuring the product; human labels pending. |
